## 2. “直接迁入”如何执行

1. **确认本轮目标并保全工作区**：查看 Git 状态和当前 HEAD；识别已有用户改动。普通同步任务不顺带改品牌、关闭授权或清理用户文件。
2. **拿到当次官方源代码**：记录仓库、分支、完整 commit SHA、获取时间、参考引擎版本。源代码可以独立放在参考目录或 worktree；若用户指定副本，先记录副本来源。参考源码只读使用。
3. **确定迁入单元**：以官方完整实现为准梳理组件、hooks、状态、事件处理、历史持久化、IPC、protobuf、依赖、样式、语言文件和资源。避免只抄可见 TSX 而形成半套新旧链路。
4. **识别本地定制交叉点**：对照下节清单，在覆盖前保存可审阅差异。可直接替换纯核心文件；混有本地定制的文件则迁入官方核心后重新接上定制，或保留必要的局部适配。
5. **保持官方协议**：客户端定义与实际官方引擎核对；不自行设计新引擎 RPC。不支持的方法先确认版本和漏迁代码，再考虑官方反馈或客户端兼容。
6. **验证两条线**：官方新增功能与原 AI Senso 入口都要验证，尤其发送参数、角色恢复、导航初始化和授权启动。按改动范围运行已有检查，注明未完成的真实环境验证。
7. **记录结果**：填写来源、文件范围、保留的定制、偏离官方的最小适配、引擎实测版本、验证命令及结果。后续提交时使同步与无关定制尽量可单独审阅；没有用户请求时不必自行推送或发布。

历史 Git 没有完整原始基线并不是必须先重建全仓历史才能同步的理由。本项目既定方式是对照迁入；有对应旧上游基线时可用三方比较辅助，没有时照样先明确本轮来源和范围。不要把直接 rebase / 全仓合并 unrelated histories 作为默认方案。

## 4. 引擎策略与版本记录

使用官方发行的引擎，维护时跟随官方最新。一次构建应先解析到确定版本，再让所有目标使用该版本，避免多平台在构建期间拿到不同版本。

当前 CI 在未指定引擎版本时通过 `scripts/ci-build-plan.js` 解析官方 latest；该实现只是构建取版，不代表已安装客户端自动升级。当前 Memfit 的部分检查 / 更新入口被关闭，是否调整由具体任务决定。

文档中至少区分：目标策略、构建所用版本、当前连接引擎版本、实际验证版本。“最新”不能替代可复现的版本号。
