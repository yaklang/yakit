# code-review

对 Yakit 仓库的代码改动产出规范化三块式 review 报告。

> 核心原则：**review 是只读的**——只记录问题，不修改被审查代码；**验证必须真实执行**——tsc 与 vitest 没有实际运行过，报告中不得标 ✅。

## 触发方式

本 skill 有三种触发途径：

1. **语义自动触发**：用户说「review 一下」「帮我审查这个 PR」「审查一下当前分支的改动」「对比 master 看看这个分支改了什么」「合并前检查一下」等——提到**当前分支 / 某个分支相对基线的改动**时同样触发。
2. **斜杠命令**：`/code-review`，可带参数，如 `/code-review review PR 4198`。
3. **被其他 skill 调用**：如 pr skill 在创建 PR 前指定 diff 范围调用本 skill——**外部调用已指定范围时直接执行，不再弹框询问审查对象**。

## 步骤一：确定审查对象

按优先级判断，输入能确定的直接用，不要多问：

| 优先级 | 条件 | 模式 |
| --- | --- | --- |
| 1 | 输入含 PR 编号（如「review 4198」「审查 #4198」） | PR 模式 |
| 2 | 输入含分支或基线（如「review dev 分支」「对比 feat-x 检查」） | 分支模式 |
| 3 | 外部 skill 已显式指定 diff 范围 | 直接采用，不弹框 |
| 4 | 以上都没有 | 用 `AskUserQuestion` 弹框 |

弹框选项（question 文本注明「审查 PR 或其他基线请在 Other 中输入编号 / 分支名」）：

- 当前分支 vs master
- 工作区未提交改动

三种模式的做法与报告文件名：

| 模式 | 获取改动 | 报告文件名（仓库根） |
| --- | --- | --- |
| PR | `gh pr view <编号> --repo yaklang/yakit --json title,headRefName,baseRefName,files` + `gh pr diff <编号>` | `PR-<编号>-review.md` |
| 分支 | `git diff <基线>...HEAD` + `git log --oneline <基线>..HEAD`，基线默认 `master` | `<分支名>-review.md`（`/` 替换为 `-`） |
| 工作区 | `git diff HEAD` + `git status --short` 中的未跟踪新文件（读文件内容纳入审查） | `working-tree-review.md` |

## 步骤二：收集与分类改动

- 用 `git diff --stat`（或 PR 模式的 files 列表）列出全部改动文件。
- 按类型分类：源码（ts/tsx/js/jsx）、测试、样式（less/css/scss）、依赖（package.json / yarn.lock）、配置、文档。
- **diff 为空 → 直接说明没有可审查改动，停止。**

## 步骤三：六维检查

逐维度审查前，先读取 [`references/check-dimensions.md`](references/check-dimensions.md) 中对应维度的检查细则。

| # | 维度 | 触发条件 | 无涉及时 |
| --- | --- | --- | --- |
| 1 | 代码逻辑 | 有源码改动 | 汇总表标 ⏭️ N/A |
| 2 | TS 定义 | 有 ts/tsx 改动 | 同上 |
| 3 | UI 引用与 Props | 有组件 / props 改动 | 同上 |
| 4 | CSS 样式 | 有样式文件或 tsx 内样式改动 | 同上 |
| 5 | 依赖版本影响 | **仅当改动清单含 package.json** | 标 ⏭️ N/A（无依赖改动） |
| 6 | 配置项影响 | **仅当改动清单含配置文件** | 标 ⏭️ N/A（无配置改动） |

硬规则：

- 维度 5、6 的条件不可放宽：**没有 package.json 改动就不审依赖，没有配置文件改动就不审配置**。
- N/A 行必须显式出现在汇总表中，不允许整行消失、不允许默默跳过。
- 配置文件指：`tsconfig*.json`、vite/vitest 配置、electron-builder 配置、`.github/workflows/`、`scripts/`、`cli/`、`.env*`、`.husky/`、`.lintstagedrc` 等；package.json 的 `scripts` 段改动也算配置改动（此时维度 5、6 同时触发）。

## 步骤四：强制验证（每次必做）

### TS 验证

改动落在哪个 TS 子项目，就对哪个跑该子项目的类型检查（tsc 是项目级检查，必须跑整个子项目，不是单文件）：

| 改动位置 | 命令 |
| --- | --- |
| `app/renderer/src/main/` | `cd app/renderer/src/main && yarn type-check` |
| `app/renderer/engine-link-startup/` | `cd app/renderer/engine-link-startup && yarn type-check` |
| 仅 `app/main/` 或不含任何 TS 子项目文件 | 跳过，报告中注明原因（Electron 主进程为纯 JS 无 tsconfig / 本次改动无 TS 文件） |

结果计分：通过 → 1 条 ✅ 正确项；失败 → 1 条 ❌ P0 问题（附报错的 `文件:行号` 摘要）。

### 测试验证

按与 CI（`scripts/ci-select-vitest-tests.js`）一致的三条规则选择相关测试：

1. 变更文件本身是 `__test__/` 下的 `*.test.*` / `*.spec.*` → 纳入；
2. 变更业务文件的同目录 `__test__/<stem>.(test|spec).*` 存在 → 纳入；
3. `__test__/` 用例 import 了某个变更模块（grep 文件路径 / `@renderer` / `@engine` 等别名匹配）→ 该用例纳入。

在仓库根执行：

```bash
yarn test:vitest <测试文件...> --run
```

- 全部通过 → 1 条 ✅（注明跑了几个文件几个用例）；有失败 → 每个失败用例记 ❌ P0（附用例名与断言失败摘要）。
- 找不到任何相关测试 → 汇总表如实标「⏭️ 无相关测试」。

### 环境异常降级

tsc / vitest 因**环境原因**无法运行（依赖未安装、node 版本不符等），而非代码本身报错时：汇总表对应行标 ⚠️「验证环境异常」，提示先执行 `yarn cli install`。**既不得标 ✅，也不得算作代码问题。**

## 步骤五：测试用例缺失检查

逐个判断改动的业务文件是否需要测试用例：

- **需要**：新增/修改了逻辑分支、纯工具函数、状态转换逻辑、复杂组件交互行为、bug 修复（防回归）。
- **不需要**：纯样式调整、纯文案/i18n、类型声明文件、构建/CI 配置本身。

需要用例但同目录不存在 `__test__/<stem>.test.*` → 记 1 条 ❌ **P1 问题「缺失测试用例」**，注明建议的测试文件路径（`<业务文件所在目录>/__test__/<stem>.test.ts`）。

## 严重程度体系

| 级别 | 含义 | 典型场景 | 对合并结论的影响 |
| --- | --- | --- | --- |
| ❌ P0 | 必须修复 | 安全漏洞、明确功能性 bug、TS 验证失败、测试验证失败 | 存在即不通过 |
| ❌ P1 | 需要修复 | 边界逻辑缺陷、props 使用与定义不符、缺失测试用例 | 存在即需要修复 |
| ⚠️ 警告 | 不阻塞合并 | 风格偏离仓库规范、冗余代码、命名建议、依赖升级缺动机说明 | 不影响结论 |

## 步骤六：输出三块报告

先在对话中完整输出，再原样写入报告文件（步骤一确定的文件名）。布局严格如下：

````markdown
# Code Review 报告：<PR 标题 / 分支名 / 工作区改动>

## 一、Review 结果汇总

| 检查项 | 结果 |
| --- | --- |
| 代码逻辑检查 | ✅ / ❌ / ⏭️ N/A |
| TS 定义检查 | ✅ / ❌ / ⏭️ N/A |
| UI 引用与 Props 检查 | ✅ / ❌ / ⏭️ N/A |
| CSS 样式检查 | ✅ / ❌ / ⏭️ N/A |
| 依赖版本影响检查 | ✅ / ❌ / ⏭️ N/A（无 package.json 改动） |
| 配置项影响检查 | ✅ / ❌ / ⏭️ N/A（无配置文件改动） |
| TS 验证（tsc） | ✅ 通过 / ❌ 失败 / ⚠️ 环境异常 / ⏭️ 跳过（原因） |
| 测试验证（vitest） | ✅ N 个文件全通过 / ❌ 失败 / ⏭️ 无相关测试 |
| 测试用例缺失检查 | ✅ 齐全 / ❌ 缺失 N 处 |

**统计：正确 X 项 / 问题 Y 项（P0 a 项 / P1 b 项）/ 警告 Z 项**

## 二、明细解释

> 布局规则：**每一项固定两行**——第一行是定位行（按类型取不同内容），第二行缩进两格写原因结果。
>
> **换行必须是硬换行**：第一行末尾补两个空格（markdown hard break），否则渲染时会并成一行；第二行行首缩进两个空格接在列表项内。

### ✅ 正确项

第一行：内容描述；第二行：原因结果。

- 内容描述（确认了什么）··
  原因结果（为什么判定正确 / 验证依据是什么）

（`··` 表示行尾两个空格，实际输出时写两个空格，不要真写点号）

### ❌ 问题项

第一行：`文件:行号` + 严重级别；第二行：原因结果（问题描述与修复建议）。

- [P0] `文件:行号`··
  原因结果：<问题是什么，为什么错> → <修复建议>
- [P1] `文件:行号`··
  原因结果：<问题是什么，为什么错> → <修复建议>

> 行号必须写：取问题对应代码的实际行号（如函数定义行）；「缺测试用例」这类不指向具体行的，用关键函数的行号（如 `envfile.tsx:178`）。不允许只写文件路径不带行号。

### ⚠️ 警告项

第一行：`文件:行号` 或标题；第二行：原因结果。

- `文件:行号` 或 <一句话标题>··
  原因结果：<说明与建议>

## 三、合并结论

**结论：不通过 / 需要修复 / 可以合并**

<判断依据：按下方映射表判定；只允许这三种结论，不得出现其它中间态>
````

统计口径：

- 每个维度整体通过（未发现问题）计 1 条正确项，明细中按两行制写明确认过的要点与依据。
- 每个具体问题 / 警告各计 1 条；TS 验证、测试验证通过各计 1 条正确项。
- ⏭️ N/A 与 ⚠️ 环境异常不计入三项统计。
- 明细中**每个条目都是两行**（定位行 + 缩进的原因结果行），不得把两行并成一行，也不得一个条目超过两行；需要展开细节时压缩进第二行的一句话里。

合并结论映射（只有三种结论，不允许出现「修复后可合并」之类的中间态）：

| 情况 | 结论 |
| --- | --- |
| 存在任一 P0 | 不通过 |
| 无 P0，存在 P1 | 需要修复 |
| 仅警告或全部正确 | 可以合并 |

## 边界情况

- **改动文件 > 50 个**：优先审查源码/依赖/配置等高风险文件，样式与文案抽检，报告开头说明覆盖度。
- **gh 未安装或未登录**：报告错误并停止；若本地分支恰好对应该 PR，经用户确认后降级为分支模式。
- **PR 模式只有 diff 没有本地上下文**：结合文件清单审查；本地存在对应分支时读本地代码补充上下文，否则报告中注明「仅基于 diff 审查」。
- **被其他 skill 调用**：按传入范围执行，落盘规则不变，三块报告全文返回给调用方。

## 禁止事项

- 修改被审查的代码（review 只读，修复与否由用户决定）。
- 运行被审查代码本体；允许执行的只有 `yarn type-check` 与 `yarn test:vitest ... --run` 两个验证命令。
- 编造验证结果；未实际运行 tsc / vitest，报告中不得标 ✅。
- 无 package.json 改动时审依赖、无配置文件改动时审配置；也不许省略汇总表的 N/A 行。
- 发现问题不报告或降级瞒报（如把明确的功能 bug 写成警告）。
