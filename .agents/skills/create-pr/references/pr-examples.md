# PR 描述生成细则与示例

本文件是 `create-pr` skill 的参考手册：生成 PR 描述的完整正例、task list 同步规则示例、合并方式判断示例、标题规则说明。SKILL.md 中「第 5 步：生成 PR 标题与描述」「第 6 步：合并方式选择」「第 7 步：创建或更新」引用本文件时按需阅读对应部分。

## 一、按模板填写的完整 PR 描述正例

### 全量版（含全部追加小节）

适用于：通过 `code-review` skill 评审发现问题 + 用户提供了关联信息（issue 编号、跨项目 PR 链接）。模板小节（改动类型 / 🔗 关联 Issue / PR / 💡 背景与方案 / 影响范围 / 合并方式）全部保留，追加小节插在「影响范围」之后、「合并方式」之前：

````markdown
## 改动类型

- [ ] 新功能（新页面 / 新选项 / 新能力）
- [x] Bug 修复（有用户可见行为修正）
- [ ] 文档改动
- [ ] 样式 / UI 调整（无逻辑变化）
- [ ] 性能优化
- [ ] 重构（不改变外部行为）
- [ ] 测试改动
- [ ] 构建 / 依赖 / 打包配置
- [ ] CI 流程改动
- [ ] 杂项（脚本 / 工程化 / 版本号）
- [ ] 其他

## 🔗 关联 Issue / PR

close #4200
https://github.com/yaklang/yaklang/pull/3210

## 💡 背景与方案

分页组件 setP 在合并 Pagination 配置后仍基于旧 sortRef 排序，导致表格翻页后排序状态错乱。本次将 sortRef 的同步时机改为基于合并后的 Pagination 判断，保证排序状态与分页配置一致。

## 影响范围

修复表格翻页后排序图标与数据顺序不一致的问题；不改变分页 API 与其它行为。UI 变化见截图（略）。

## 代码评审结论

**结论：需要修复**（正确 6 项 / 问题 2 项（P0 0 项 / P1 2 项）/ 警告 2 项）

## 建议合并前修复的问题

- [ ] `src/components/Table/Pagination.tsx:178` setP 中 sortRef 赋值发生在 mergePagination 之前，极端场景下仍会读到旧值
- [ ] `src/hooks/useSort.ts:42` 排序回调缺少空值保护，columns 为空时会抛错

## 合并方式

- [ ] Create a merge commit（保留完整提交历史）
- [x] Squash and merge（压缩为一条提交）
- [ ] Rebase and merge（线性历史）
````

要点：

- 改动类型只勾选**最贴近主目的**的一项（以用户感知的主要结果为准），不按改动文件数量勾选多项；确属复合目的时最多勾两项。
- 「关联 Issue / PR」可同时包含本仓库 issue（`close #xxxx` 等）与其它项目/仓库的 PR 链接（直接贴完整 URL，如 yaklang 引擎 PR）；只有用户输入明确提到才填，否则填 `None`，不编造编号或链接。
- 「代码评审结论」为**必需小节**（第 4 步强制通过 `code-review` skill 评审）：格式为 `**结论：<不通过/需要修复/可以合并>**（<报告统计行>）`，放在「建议合并前修复的问题」之前；更新 PR 时该节以最新评审结果**覆盖重写**，不累积。

### 精简版（无问题、无引擎链接）

适用前提：评审无建议合并前修复的问题（结论为「可以合并」）+ 用户未提到任何关联信息。「建议合并前修复的问题」整节省略（不要生成空小节）；「代码评审结论」为必需小节，始终保留（如 `**结论：可以合并**（正确 9 项 / 问题 0 项 / 警告 1 项）`）。「关联 Issue / PR」填 `None`：

````markdown
## 改动类型

- [ ] 新功能（新页面 / 新选项 / 新能力）
- [ ] Bug 修复（有用户可见行为修正）
- [ ] 文档改动
- [ ] 样式 / UI 调整（无逻辑变化）
- [ ] 性能优化
- [x] 重构（不改变外部行为）
- [ ] 测试改动
- [ ] 构建 / 依赖 / 打包配置
- [ ] CI 流程改动
- [ ] 杂项（脚本 / 工程化 / 版本号）
- [ ] 其他

## 🔗 关联 Issue / PR

None

## 💡 背景与方案

记事本模块状态管理分散在多个组件内部，props 层层透传。本次将文档状态收敛到统一 store，组件仅消费，不改变任何外部行为。

## 影响范围

不改变用户可见行为，纯内部重构。

## 代码评审结论

**结论：可以合并**（正确 9 项 / 问题 0 项 / 警告 1 项）

## 合并方式

- [ ] Create a merge commit（保留完整提交历史）
- [ ] Squash and merge（压缩为一条提交）
- [x] Rebase and merge（线性历史）
````

### 回退结构（模板文件不存在时）

当前分支早于模板合入、`.github/PULL_REQUEST_TEMPLATE.md` 不存在时，使用以下约定结构（与模板小节对应，仅去掉了 emoji 标题）：

````markdown
## 概述

（一两句话说明本 PR 做了什么、为什么）

## 关联 Issue / PR

（本仓库 issue：close #xxxx；其它项目/仓库的 PR 链接直接贴 URL；无关联填 None）

## 改动内容

### <主题小节>
（关键文件与行为变化；按模块/主题分节，不逐文件罗列）

## 影响范围

（用户可见的行为变化；纯重构需说明「不改变用户可见行为」）

## 代码评审结论

**结论：<不通过/需要修复/可以合并>**（<报告统计行>）

## 建议合并前修复的问题

- [ ] `src/xxx.ts:123` <问题描述>

## 合并方式

请使用 **<合并方式文案>** 合并。
````

回退结构的「合并方式」文案对应：merge → `Create a merge commit`；squash → `Squash and merge`；rebase → `Rebase and merge`，必须完整写出整节（含 `## 合并方式` 标题与加粗文案）。

## 二、task list 同步规则示例（更新已有 PR 时）

更新 OPEN 状态 PR 的描述前，必须重新评审并按以下规则同步「建议合并前修复的问题」小节：

**场景：旧描述 → 本次评审后的新描述**

旧 PR 描述：

```markdown
## 建议合并前修复的问题

- [ ] `src/a.ts:10` 空值未保护
- [x] ~~`src/b.ts:20` 边界计算溢出~~（✅ 已修复：abc1234）
- `src/c.ts:30` 缺少错误处理
```

本次评审发现：`a.ts` 问题仍在；`b.ts` 已确认修复（本次评审无此问题）；`c.ts` 仍未修复；新发现 `d.ts:40` 问题。同步结果：

```markdown
## 建议合并前修复的问题

- [ ] `src/a.ts:10` 空值未保护
- [x] ~~`src/b.ts:20` 边界计算溢出~~（✅ 已修复：abc1234）
- [ ] `src/c.ts:30` 缺少错误处理
- [ ] `src/d.ts:40` 新发现的定时器未清理问题
```

规则逐条对应：

| 旧条目状态 | 本次评审结论 | 处理 |
| --- | --- | --- |
| `- [ ]` 未修复 | 仍未修复 | 原样保留 |
| `- [ ]` 未修复 | 已在代码中修复 | 改为 `- [x] ~~原描述~~（✅ 已修复：<修复 commit 短哈希>）`，不删除 |
| `- [x]` 已修复（带 ✅ 标注） | 任意 | 原样保留，不删除、不改勾选状态 |
| 普通列表条目（无复选框） | 任意（未修复） | 迁移时改写为 `- [ ]`，内容保留 |
| 无条目 | 新发现的问题 | 以 `- [ ]` 追加 |

**CLOSED / MERGED 后重建不迁移**：旧 PR 已关闭时按新建流程生成描述，「建议合并前修复的问题」只包含**本次评审**发现的问题，不迁移旧 PR 的任何历史条目（含已修复标注）。

## 三、合并方式判断示例

合并方式按第 6 步三级优先级确定，本表仅对应**优先级 3（自动选择）**：新建 PR，或更新已有 PR 但旧描述无有效勾选时适用。用户输入未指定且需自动选择时，用 `git log origin/master..HEAD --format='%an'` 统计作者数（去重）与 commit 总数，按下表从上到下互斥匹配：

| 场景 | commit 数 | 作者数 | 结论 |
| --- | --- | --- | --- |
| 单次提交 | 1 | 1 | **rebase**（无需压缩也无多人协作） |
| 同人少量提交 | 2–3 | 1 | **squash**（压成一条干净历史） |
| 多人协作 | 任意 | 2 | **merge**（保留完整提交历史，作者数规则优先） |
| 同人大量提交 | 4 | 1 | **merge**（commit 数 > 3，保留历史） |

**保留旧勾选示例（优先级 2，更新已有 PR 时最常见）**：

| 场景 | 用户本次输入 | 旧 PR 描述勾选 | 最终勾选 | 说明 |
| --- | --- | --- | --- | --- |
| 沿用旧选择 | 未提合并方式 | squash | **squash**（原样迁移） | 即使本次自动规则算出 merge 也不覆盖 |
| 旧描述无勾选 | 未提合并方式 | 三项都未勾/无该小节 | 按自动规则计算 | 回退优先级 3 |
| 本次意愿优先 | 「用 rebase 合并」 | squash | **rebase** | 用户指定（优先级 1）永远压过旧勾选 |

判断结果写入 PR 描述「## 合并方式」小节时勾选对应一项（保留三项完整文案）：

```markdown
## 合并方式

- [ ] Create a merge commit（保留完整提交历史）
- [x] Squash and merge（压缩为一条提交）
- [ ] Rebase and merge（线性历史）
```

注意：**优先级顺序**——① 用户输入指定直接使用；② 更新已有 OPEN PR 且未指定时沿用旧描述勾选（防止 `gh pr edit --body` 整段替换覆盖掉之前手动选定的方式）；③ 自动规则按表匹配——**作者数 ≥ 2 或 commit 数 > 3 归 merge，commit 数 = 1 归 rebase，其余（2–3 个同人 commit）归 squash**。

## 四、标题规则说明

**PR 标题基于分支全部 commit 归纳生成（`type: subject`，中文为主），不使用分支名**：

- 取材：`git log origin/master..HEAD` 的全部 commit。单个 commit 直接用其标题；多个 commit 归纳**主语义**为一个更高层概括，不逐条罗列。
- 格式：与 `commit-msg` skill 规范一致——结尾无句号、不带 `(#PR号)` 后缀、尽量 72 字符内（中文按 2 计）；type 按用户感知的主要结果选取（feat/fix/docs/style/perf/refactor/test/build/ci/chore）。
- 示例：
  - 分支 `hejiahui/fix/tree` 上单个 commit `fix: 修复文件树节点白缝与右键菜单丢失边框阴影` → PR 标题即 `fix: 修复文件树节点白缝与右键菜单丢失边框阴影`。
  - 分支 `luoluo/perf/ai-model-thought` 上多个关于 AI 模型思考强度的 commit → 归纳为 `perf: 优化 AI 模型思考强度的配置与展示`（概括，不罗列每个 commit）。

**更新已有 PR 时的智能替换**：

| 旧标题 | 处理 | 说明 |
| --- | --- | --- |
| == 当前分支名（旧规则产物） | 替换为本次 commit 总结标题 | 旧标题无信息量，升级为总结标题 |
| ≠ 分支名（人工改过或已是总结标题） | **保留旧标题，不覆盖** | 与合并方式「沿用旧勾选」逻辑对称，尊重人工选择 |

**为什么每次 `gh pr edit` 都必须显式带 `--title`**：`gh pr edit` 更新 body 时若省略 `--title`，部分版本会把标题改回远端默认值或保留旧值，导致标题失控；显式带上最终标题（本次总结标题或保留的旧标题）可确保每次更新后标题确定不变。因此无论新建（`gh pr create --title`）还是更新（`gh pr edit --title`）都必须显式传标题，并在创建/更新后回读验证（`gh pr view --json title,body`）。

## 五、手动模式输出示例（gh 降级流程中用户选择「手动创建 PR」时）

本机没有 gh（或未登录）且用户选择手动创建时，前 6 步正常执行，第 7 步不执行任何 `gh` 命令、不生成任何文件，标题与描述直接在对话框中展示供复制。以下为分支 `hejiahui/fix/tree` 的输出示例（agent 向用户报告的话术）：

````markdown
本机 gh 不可用，已按手动模式完成 commit、push 与代码评审。以下内容供复制：

- **PR 标题**（打开创建页后粘贴到 Title 输入框）：

  ```
  fix: 修复文件树节点白缝与右键菜单丢失边框阴影
  ```

- **创建入口**（浏览器打开，Title 粘贴上面的标题代码块，Description 粘贴下面的描述代码块全文）：
  https://github.com/yaklang/yakit/compare/master...hejiahui/fix/tree?expand=1

- **查重提醒**：打开创建页后若提示该分支已有 open PR，请改为在该 PR 页面编辑描述，不要重复创建。

- **旧内容提醒**：本机读不到已有 PR 的旧描述；若该分支已有 PR，可把旧描述全文粘贴给我，按同步规则重新生成合并版（改动类型勾选 / 关联 Issue / PR / 合并方式勾选 / 问题清单累积），或自行把旧内容合并进新描述。

**PR 描述**（粘贴到 Description 输入框）：

```
## 改动类型

- [ ] 新功能（新页面 / 新选项 / 新能力）
- [x] Bug 修复（有用户可见行为修正）
（……其余小节同正常生成的描述，含代码评审结论、建议合并前修复的问题、合并方式勾选……）
```
````

注意：

- 标题与描述都以**代码块**展示，保证用户复制到的是 markdown 源码而非渲染后的文本；描述再长也完整输出，不截断、不落盘成文件。
- 手动模式下没有回读验证与查重，报告话术必须包含「查重提醒」，由用户在创建页自行确认分支是否已有 PR。
- 生成的内容默认**不含**旧 PR 的任何旧内容（没有 gh 读不到旧描述）；用户粘贴旧 PR 描述全文时，按 SKILL.md 第 7 步同步规则（改动类型勾选、关联 Issue / PR、合并方式勾选、问题 task list 累积）合并生成。
- 任务在用户手动创建 PR 前结束，agent 不等待创建结果、不介入后续更新。
