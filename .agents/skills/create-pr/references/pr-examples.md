# PR 描述补充示例

主流程与字段规则见 [SKILL.md](../SKILL.md) 第 5–7 步。按场景读取下列小节；仓库有 `.github/PULL_REQUEST_TEMPLATE.md` 时直接使用实际模板。

## 按模板填写的补充说明

改动类型按主流程第 5 步结合完整提交信息、diff 和基线归因确认，重复类型只勾选一次。例如：

- `feat` 新增导出功能，后续 `fix` 修补该新功能的空值处理，`test` 补充测试：勾选新功能、测试改动，不额外勾选 Bug 修复。
- `feat` 新增导出功能，`fix` 修复基线已有的分页排序错误，`test` 补充测试：同时勾选新功能、Bug 修复、测试改动。

更新已有 PR 时保留旧勾选并补充已确认的新类型；PR 标题仍为单行，合并方式仍只选一项。

背景与方案示例：

> 分页配置合并后，排序仍读取旧 sortRef，导致翻页后排序错乱。本次调整 sortRef 同步时机，使排序与合并后的分页配置一致。

模板外的评审结论和问题清单按主流程第 5 步追加；评审统计取实际报告。没有当前 P0/P1 且没有历史问题时省略问题小节。

## 回退结构（仅模板文件不存在时）

使用以下结构；占位内容按实际证据填写，问题小节按第 5、7 步决定是否保留。「改动类型」按第 5 步多选，更新时按第 7 步保留旧勾选并补充。「合并方式」完整保留三项，并按第 6 步勾选其中一项。

```markdown
## 概述

<一两句话说明做了什么、为什么>

## 改动类型

- [ ] 新功能（新页面 / 新选项 / 新能力）
- [ ] Bug 修复（有用户可见行为修正）
- [ ] 文档改动
- [ ] 样式 / UI 调整（无逻辑变化）
- [ ] 性能优化
- [ ] 重构（不改变外部行为）
- [ ] 测试改动
- [ ] 构建 / 依赖 / 打包配置
- [ ] CI 流程改动
- [ ] 杂项（脚本 / 工程化 / 版本号）
- [ ] 其他

## 关联 Issue / PR

<用户提供的关联；更新时合并旧关联；无关联填 None>

## 改动内容

### <主题>

<关键文件与行为变化，按模块或主题组织>

## 影响范围

<用户可见变化；纯重构说明不改变用户可见行为>

## 代码评审结论

**结论：<不通过/需要修复/可以合并>**（<实际报告统计行>）

## 建议合并前修复的问题

- [ ] `src/xxx.ts:123` <问题描述>

## 合并方式

- [ ] Create a merge commit（保留完整提交历史）
- [ ] Squash and merge（压缩为一条提交）
- [ ] Rebase and merge（线性历史）
```

## 历史问题复发示例（更新 OPEN PR 时）

旧条目：

```markdown
- [x] ~~`src/b.ts:20` 边界计算溢出~~（✅ 已修复：abc1234）
```

本次复核确认同一缺陷复发，直接更新原条目：

```markdown
- [ ] `src/b.ts:20` 边界计算溢出（曾修复：abc1234；本次复核：已复发）
```

后续确认 `def5678` 再次修复该问题，仍更新同一条目，保留前次修复与复发记录：

```markdown
- [x] ~~`src/b.ts:20` 边界计算溢出~~（曾修复：abc1234；曾复核：已复发；✅ 已修复：def5678）
```

若再次复发，保留上述历史，将 `def5678` 标为「曾修复」，取消勾选和删除线，并追加本次复发记录。重复复核同一状态与证据不重复追加。

不要同时保留旧勾选条目并追加相同缺陷。其它状态按第 7 步处理；报告未提及旧问题不等于确认修复，须复核当前代码。

## 合并方式判断示例

分支有 4 个 commit、同一作者，旧 OPEN PR 勾选 squash：用户本次未指定时沿用 squash；明确指定 rebase 时改用 rebase；没有旧有效勾选且用户未指定时，自动选择 merge。优先级与完整决策表见第 6 步。

## 手动模式报告补充

输出格式遵循主流程「手动模式」。报告明确说明「PR 尚未创建」，提交、评审、推送及远端 OID 核验只报告实际完成的状态；不要把描述生成视为 PR 已创建。
